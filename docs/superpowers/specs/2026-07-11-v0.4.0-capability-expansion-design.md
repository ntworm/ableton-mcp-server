# v0.4.0 Capability Expansion Design

## Purpose

Deliver a coherent v0.4.0 expansion of `ableton-mcp-server` without inheriting
stale assumptions from the existing proposal files. The release adds the safe,
testable capability gaps identified from `pnomolos/live-wire` and
`hidingwill/AbletonBridge`, plus device parameter writes, while preserving the
current hybrid bridge, explicit mutation allowlist, deferred verification, and
single-undo batch behavior.

The implementation starts from local `main` at `ce7fe9c` on the isolated branch
`feature/v0.4.0-implementation`. The earlier feature branch and its untracked
plan remain untouched.

## Corrected scope

The baseline exposes 46 public MCP tools. v0.4.0 adds ten genuinely new tools,
for a final total of 56:

1. `set_parameter_value`
2. `get_clip_info`
3. `get_session_overview`
4. `search_browser`
5. `delete_clip`
6. `clear_clip_notes`
7. `fire_scene`
8. `set_track_property`
9. `set_clip_properties`
10. `create_clip_automation`

`load_device_to_track` is already one of the 46 baseline tools. v0.4.0 will
harden its tests, timeout, documentation, and capability reporting, but will
not register a duplicate tool.

The existing `add_notes_to_clip` payload gains optional `probability`,
`release_velocity`, and `velocity_deviation` fields. `get_bridge_status` gains
backward-compatible capability metadata. An internal compound helper may
compose track creation and device loading, but is not public MCP surface.

## Architecture and routing

The public Python MCP layer remains responsible for Pydantic validation,
documentation, error containment, and routing. Root `contracts.py` remains the
canonical command registry and timeout policy; its vendored Remote Script copy
is always generated by `scripts/vendor_contracts.py`.

TCP/Remote Script owns all new commands. In particular, `search_browser` is a
read-only traversal of the existing `application.browser` object and stays on
TCP port 9888. This avoids making a basic discovery command depend on the
optional Extension. The existing WebSocket route remains responsible for
`get_warp_state`, `set_warp_state`, and `load_device_to_track`.

The socket thread never touches Live's Python LOM. Synchronous reads execute
through the existing UI-thread request queue. Writes that may settle over Live
ticks use command generators with bounded write/yield/readback retries.
Standalone mutations own one undo step. `run_batch` owns one outer undo step,
stops at the first error, and never claims rollback.

## Feature behavior

### Device parameter writes

`set_parameter_value(track_index, device_index, parameter_name, value)` resolves
the exact parameter on Live's UI thread. It rejects missing devices, unknown
parameters, disabled parameters, and values outside the parameter's `[min,max]`
range. Unknown names include up to three close candidates. It writes, yields,
reads the observed value, retries once when necessary, and returns both target
and observed values. Quantized parameters accept Live's documented quantized
result when it is a valid in-range value; continuous parameters require the
existing numeric tolerance. The command is allowed inside `run_batch`.

### Read-side tools

`get_clip_info` returns a stable metadata dictionary and represents empty slots
as `has_clip: false`. `get_session_overview` composes existing reads locally in
the MCP layer so it does not add a redundant remote command or oversized
single handler. `search_browser` performs bounded case-insensitive depth-first
search with a clamped result limit and traversal budget. It returns display
names, URIs when exposed, categories, and whether an item is loadable.

`get_bridge_status` keeps all existing keys and adds server version, tool count,
registered WS methods, Extension availability, Python runtime, and a fixed
feature whitelist. It never returns environment variables, credentials, or
filesystem paths beyond fields already in the existing public contract.

### Clip, scene, and track mutations

`delete_clip`, `clear_clip_notes`, and `fire_scene` use direct LOM operations
inside the UI-thread dispatcher and return observed result summaries.
`clear_clip_notes` is deferred and re-reads the clip so `notes_removed` is an
observed delta rather than an estimate.

`set_track_property` accepts only `mute`, `solo`, or `arm`. Arm rejects track
types that cannot be armed. `set_clip_properties` requires at least one of
`loop_start`, `loop_end`, or `name`, validates the final loop interval before
writing, and verifies each requested attribute across ticks. Numeric, boolean,
and string verification share object-generic helpers.

### Session clip automation

`create_clip_automation` operates only on Session clips. It resolves mixer
parameters (`volume`, `pan`, and indexed sends) or exact device parameter names,
requires an enabled automatable parameter, clamps input size to 500 points, and
validates finite times plus values within the parameter bounds. The handler
checks for the required Live automation-envelope APIs and returns a structured
unsupported/capability error when the host does not expose them. It clears only
the selected parameter envelope, inserts ordered breakpoints, yields, and
verifies that the clip reports envelopes. It does not implement Arrangement
automation or track automation.

### Extended MIDI notes

The optional note-expression fields are passed only when both the request and
the host note specification expose the corresponding property. Unsupported
fields produce an explicit capability error rather than being silently ignored.
Old five-field note payloads remain unchanged.

## Error model and safety

All expected failures remain structured bridge errors. Invalid indices, enums,
ranges, empty queries, and missing payload fields are validation errors. Wrong
track/clip kinds use `WRONG_TYPE`. Missing Live APIs or convergence failures use
the existing availability/internal error taxonomy with actionable messages.
Network ambiguity never triggers automatic mutation replay.

Browser traversal is bounded by result limit, depth, per-node child cap, and a
global visited-node budget. Responses must remain below the existing JSONL frame
limit. Path IDs remain session-local index locators and are not redesigned.

## Testing strategy

Every production behavior is implemented red-green-refactor. Tests are placed
with the current repository structure rather than the stale `tests/test_server.py`
references:

- public registration, docstrings, and forwarding: `tests/test_server_tools.py`;
- model and batch validation: `tests/test_models.py`;
- contracts and vendoring: `tests/test_contracts.py`, `tests/test_vendoring.py`;
- Remote Script reads and mutations: focused new test modules plus
  `tests/remote_fakes.py`;
- WebSocket hardening for existing device loading: `tests/test_ws_client.py`;
- offline bridge integration: `tests/test_mock_integration.py`;
- diagnostics capability payload: `tests/test_diagnostics.py`.

Each logical milestone ends with focused tests, the full Python suite, Ruff,
and mypy. Contract edits regenerate and verify `_contracts.py`. The final gate
also runs coverage, tool-count checks, and the Extension build. Real-Live
acceptance remains an owner-run step against a disposable Set; offline tests do
not claim to prove Live connectivity or undo behavior.

## Git and release flow

Commits are small and buildable: baseline lint cleanup; design/plan; verification
helpers and fakes; parameter writes; read tools; simple mutations; deferred
mutations and automation; MIDI/capability/timeout polish; documentation/version;
final verification fixes. No unrelated user changes are included.

After all automated gates pass, the branch is presented for final review. There
is no push, merge, or tag before owner approval. After approval, merge to `main`
with an explicit merge commit, rerun the release gate on `main`, and create the
annotated `v0.4.0` tag. Pushing the branch, main, or tag requires separate owner
authorization.

## Explicit non-goals

Reflection primitives, M4L/OSC bridges, browser persistence, web dashboards,
Arrangement editing, track-level automation, follow actions, modulation maps,
vendor-specific CC maps, ElevenLabs tools, and vendoring competitor code remain
out of scope.
