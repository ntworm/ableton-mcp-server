# Set Lifecycle and Mix Analysis Design

## Purpose

Deliver two complementary capability expansions identified during the
2026-07-12 competitive analysis of `mlmil/Ableton-Live-MCP-ULTRA-v2` and
`motodigitalguru-beep/ableton-mcp-extended`. The release adds (1) safe set
lifecycle and timed fader automation inside Live and (2) offline mix analysis
utilities, while preserving the current hybrid bridge, explicit mutation
allowlist, deferred verification, and single-undo batch behavior.

The two expansions are intentionally delivered as separate work items because
they have independent risk profiles, dependency profiles, and reviewer
populations. Lifecycle and fade grow the public Remote Script surface; mix
analysis lives entirely on the Python MCP server and never crosses the Live
boundary. Mixing them in a single release would obscure which behavior changes
when and would make rollback surgical only by revert.

## Source references and license posture

- `mlmil/Ableton-Live-MCP-ULTRA-v2`: source derived from inline review of the
  upstream `Ableton_Live_MCP/bridge.py` handlers `_rpc_lifecycle_status`,
  `_rpc_save_set`, `_rpc_quit_ableton`, and `_rpc_fade`. The MIT license on
  `bschoepke/ableton-live-mcp` (the upstream of mlmil) permits integration
  with attribution. The Remote Script runtime identity for the new wrapped
  commands is bumped to `set-lifecycle-and-fade-1`. No code is copied
  verbatim: every handler is rewritten against the existing
  `_dispatch_command_steps` / `_verified_*_steps` primitives and the existing
  `_required` / `_integer_param` / `_float_param` parameter helpers, so the
  patches read as continuous code with the surrounding handlers and not as a
  dropped-in fork.
- `motodigitalguru-beep/ableton-mcp-extended`: source reviewed for the
  offline mix analysis surface. The implementation is rewritten against
  `numpy`, `soundfile`, and the public pydantic contracts. No source is
  copied verbatim; the public function names use the existing
  `..._to_dict` envelope pattern. Where motodigitalguru exposes
  `auto_fix_masking`, our release exposes the **read-side** only: analysis
  utilities that return structured findings plus an opt-in suggestion, so
  the agent still has to choose to apply EQ changes through the existing
  `set_parameter_value` flow.

## Corrected scope

### Lifecycle and fade PR

The baseline exposes the public MCP surface registered in
`ableton_mcp_server/server.py:PUBLIC_TOOL_NAMES`. This release adds four
genuinely new tools:

1. `lifecycle_status` — read-only availability and capability probe.
2. `save_set` — perform `Song.save()` when Live exposes it; otherwise return
   a structured GUI-workflow response.
3. `quit_ableton` — save first, schedule `Application.quit` after
   `quit_delay_ticks` UI ticks, or return a structured GUI-workflow response.
4. `live_fade` — stepped fader fade on a track's mixer volume using
   smoothstep or linear interpolation, executed on the Live main thread.

`live_fade` replaces the dozens of `create_clip_automation` invocations a
script would otherwise need to write a smooth volume transition. The
existing `set_parameter_value` tool continues to cover non-fader parameter
writes; `create_clip_automation` continues to cover Session-clip envelopes.
The PR adds no `run_batch` semantics changes; lifecycle commands are
capable of being batched through the existing `run_batch` flow because they
fit the existing mutation allowlist shape.

### Mix analysis PR

This PR adds four genuinely new tools, all read-only:

1. `analyze_audio` — return LUFS-I, true-peak, RMS, and a per-band summary
   for a local file path.
2. `find_frequency_masking` — given two paths, return per-band masking
   scores between candidate and reference.
3. `analyze_mix` — given a list of paths (stems), return inter-stem masking
   plus aggregate LUFS-I.
4. `extract_single_cycle` — given a path, return a candidate single-cycle
   wavetable suitable for import into Wavetable devices.

`auto_fix_masking` is **explicitly excluded**: applying EQ fixes belongs to
`set_parameter_value` and `create_clip_automation` already. Adding a
separate mutator would split the safety model. The analysis tools only
suggest; the agent must use existing mutators to apply.

`configure_sidechain` and `capture_track_to_wav` are also excluded because
they require Live in scope; they would belong to a future "live-side audio
inspection" PR.

## Architecture and routing

### Lifecycle and fade

The public Python MCP layer remains responsible for Pydantic validation,
documentation, error containment, and routing. Root `contracts.py` remains
the canonical command registry and timeout policy; its vendored Remote
Script copy is always generated by `scripts/vendor_contracts.py`.

TCP/Remote Script owns the four new commands. The socket thread never
touches Live's Python LOM. Synchronous reads execute through the existing
UI-thread request queue. Writes that may settle over Live ticks use command
generators with bounded write/yield/readback retries.

`live_fade` is the first command that intentionally blocks the Live main
thread. The handler enters a `time.sleep` loop on the Live main thread for
`duration` seconds; the Remote Script dispatcher surfaces this as a
synchronous generator whose total work units equal `steps + 1`. The Python
MCP layer auto-raises the RPC timeout to `max(scaled, duration + 10.0)` so
the higher-level timeout policy still applies. The 60-second cap and
40-step default follow the upstream behavior; both constants are renamed
to `_LIVE_FADE_MAX_DURATION` and `_LIVE_FADE_DEFAULT_STEPS` and live in the
Remote Script module-level scope.

### Mix analysis

`ableton_mcp_server/analysis/audio.py` is a new dependency-free-on-Live
module. Public functions take filesystem paths and return structured
dicts; the MCP layer wraps each function in a tool. There is no bridge
call, no Remote Script, and no Live dependency. Tests exercise the
functions against deterministic synthesized signals.

## Feature behavior

### `lifecycle_status`

`lifecycle_status()` reads the Live object once and returns:

- `song_save_attrs` — the names of the save-related attributes exposed by
  the Live `Song` object.
- `app_lifecycle_attrs` — the names of the lifecycle attributes exposed by
  the Live `Application` object.
- `song_save_available` — `True` when `Song.save` is callable.
- `app_quit_available` — `True` when `Application.quit` is callable.
- `gui_workflow` — structured fallback steps for both `save` and `quit`
  plus notes about locked/asleep displays.

The handler never raises: missing attributes degrade to `False` flags and an
empty `gui_workflow`. The Python MCP layer exposes this with no parameters.

### `save_set`

`save_set(require_api: bool = False)` performs `Song.save()` when callable
and returns `{"saved": True, "api_available": True, "result": <value>}`.
When `Song.save` is missing, the handler returns a structured response that
includes `api_available: False` plus the `gui_workflow` payload. When
`require_api` is `True` and the API is missing, the handler raises a
`RemoteError("BAD_INPUT", "Live Song object does not expose save(); use
the GUI save workflow")`.

### `quit_ableton`

`quit_ableton(save: bool = True, force_without_save: bool = False,
quit_delay_ticks: int = 2)` always saves first when `save` is `True`. When
the save API is unavailable and `force_without_save` is `False`, the
handler returns a structured refusal including `gui_workflow`. When the
quit API is unavailable, the handler returns a structured fallback
including the quit `gui_workflow`. When both APIs are available, the
handler schedules `Application.quit` via `schedule_message(quit_delay_ticks,
...)` and returns `{"quit_requested": True, "scheduled": True, ...}` so the
RPC response can leave before Live actually closes.

### `live_fade`

`live_fade(track_selector, target_percent | target_value, duration: float =
10.0, steps: int = 40, curve: "smoothstep" | "linear" = "smoothstep",
allow_over_unity: bool = False)` resolves the track through the existing
`_resolve_track_id` helper, reads the mixer volume parameter, validates
the requested `target_value` is within `[param.min, param.max]`, and steps
the value through the requested curve. `target_percent` divides by 100 and
scales by the Live "unity" value `0.85`. `duration` is clamped to
`[0, 60]` seconds; `steps` to `[1, ∞)`. The handler records
`final_percent`, `final_value`, `display`, `start_value`, `target_value`,
`duration`, and `steps`. Errors (`target_percent > 100` without
`allow_over_unity`, invalid curve, etc) raise structured `RemoteError`
with `INVALID_PARAMS`.

### `analyze_audio`

`analyze_audio(path: str)` reads the file via `soundfile.read`, computes
LUFS-I approximation (mean square per 400 ms block with K-weighted
headroom), true-peak via 4× oversample maximum absolute amplitude, RMS,
and per-band energy summary (low/mid/high split at 250 Hz and 4 kHz),
returning a dict with the four numeric values plus the duration and
sample rate.

### `find_frequency_masking`

`find_frequency_masking(target_path: str, reference_path: str)` loads both
files (mono-ized on read), computes 1024-point STFT, and returns a list of
band masks where target energy exceeds reference energy by more than a
caller-supplied `threshold_db`. The default threshold is 6 dB. Returns
`{"bands": [{"start_hz", "end_hz", "target_db", "reference_db", "excess_db"},
...], "score": float}`.

### `analyze_mix`

`analyze_mix(stems: list[str])` runs `analyze_audio` on each stem and
returns per-stem metrics plus pair-wise masking across all stem pairs. The
pair-wise scan is `O(N²)`; the implementation caps `N` at 16 with a clear
`TRACK_LIMIT_REACHED` analog for `N > 16`.

### `extract_single_cycle`

`extract_single_cycle(path: str, frame_size: int = 2048)` finds a
candidate loop length by autocorrelation of the file's first 5 seconds,
returns the candidate single-cycle buffer plus its detected pitch in Hz.
When no clear period is found, returns `{"ok": False, "reason":
"no clear periodicity"}`.

## Error model and safety

All expected failures remain structured bridge errors for the four Live-side
commands. Validation errors use `INVALID_PARAMS` or `BAD_INPUT`. Missing
Live APIs use `LIVE_UNAVAILABLE` (existing taxonomy). Mix-analysis tools
return Python exceptions converted to the standard `_explicit_json_result`
error envelope and never raise across the MCP boundary; missing files,
unsupported encodings, and decimation failures return a structured
`{"ok": False, "reason": ...}` payload. The contract never claims rollback
for any of these tools.

`live_fade`'s main-thread block is bounded to 60 seconds; the Python MCP
client raises the RPC timeout to `duration + 10` so the dispatcher cannot
leak requests past the fade. The Remote Script dispatcher caps `steps` at
the default 40 and refuses `duration > 60` outright.

## Testing strategy

Every production behavior is implemented red-green-refactor. Tests are
placed with the current repository structure:

- public registration, docstrings, and forwarding: `tests/test_server_tools.py`;
- model and batch validation: `tests/test_models.py`;
- contracts and vendoring: `tests/test_contracts.py`, `tests/test_vendoring.py`;
- Remote Script reads and mutations: focused new test modules plus
  `tests/remote_fakes.py`;
- mix analysis: deterministic signal synthesis in `tests/analysis_synth.py`
  with assertions on numeric tolerance per spec section;
- offline bridge integration: `tests/test_mock_integration.py`.

Each logical milestone ends with focused tests, the full Python suite, Ruff,
and mypy. Contract edits regenerate and verify `_contracts.py`. The final
gate also runs coverage, tool-count checks, and the Extension build.
Real-Live acceptance for the lifecycle and fade PR remains an owner-run
step against a disposable Set; offline tests do not claim to prove Live
connectivity or undo behavior. Mix analysis tests run entirely on
`/tmp/synth.wav` synthesized via `numpy` and require no Live or Remote
Script instance.

## Git and release flow

Commits are small and buildable: lifecycle dependency-free baseline helper;
lifecycle_status read; save_set conditional; quit_ableton scheduling;
live_fade generator; mix analysis synth utility; mix analysis public
functions; mix analysis MCP wrappers; registry inflation and docs. No
unrelated user changes are included.

After all automated gates pass, the branch is presented for final review.
There is no push, merge, or tag before owner approval. After approval,
merge to `main` with an explicit merge commit, rerun the release gate on
`main`, and create the annotated `v0.5.0` tag. Pushing the branch, main,
or tag requires separate owner authorization.

## Explicit non-goals

Reflection primitives, M4L/OSC bridges, browser persistence, web
dashboards, Arrangement editing, track-level automation, follow actions,
modulation maps, vendor-specific CC maps, ElevenLabs tools, vendoring
competitor code verbatim, live-side audio inspection tools, and applying
EQ fixes from the analysis tools remain out of scope.
